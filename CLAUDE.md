# onetime

Public site for sharing a secret (password, token, credentials) through a link that works once, plus an in-browser password/token/UUID generator. No accounts. README.md describes the behaviour and API.

## Rules that must hold

- The server never sees plaintext or keys. The browser encrypts (AES-256-GCM); the key stays in the URL fragment (`/#<id>.<key>`). Nothing may send the fragment, the key or the plaintext anywhere: no analytics, no third-party requests, no logging of them. Nothing on the app origin (`https://onetimepass.pages.dev`: `/`, `/command-line`, `404.html`, `/cli/*`, the API) loads or references Google or any other third-party code; analytics exists only on the separate info site `https://onetimepass-info.pages.dev` (see "Analytics").
- A link works once. Reveal is one atomic SQL statement (`DELETE ... WHERE id = ? AND expires_at > ? RETURNING blob`). Never SELECT then DELETE.
- Only `POST /api/secrets/<id>/reveal` burns a secret. GET requests (link previews, prefetch) must not.
- Expired secrets are never handed out (checked on every read). Their rows are purged on later API requests, not by a timer; keep the README and page text saying exactly that.
- No IPs, IP hashes, cookies or request logs, because paths contain secret ids. Pages configs reject the `observability` key, so logging is controlled in the dashboard: keep Functions logs and Logpush off there.
- Strict CSP in `public/_headers`: no inline script or style, no external origins, exactly one CSP line (in `/*`, no `!` detach lines, no Google host); the info build derives its own `_headers` with `INFO_CSP` (`headersForInfo`). `Cache-Control: no-store` on the HTML, immutable on `/assets/*`; do not put Cache-Control on `/*` (Pages merges matching rules).
- The upload body is read as a counted stream that stops at the blob limit (`MAX_BLOB_BYTES`); do not go back to `request.arrayBuffer()`.
- The HTTP API contract is shared by `src/web/api.ts` and `src/worker/index.ts`; limits live in `src/shared/limits.ts`.

## Stack and layout

- Vanilla TypeScript + Vite (`index.html`, `src/web/`), output `dist/` (the app site). A second build, `ONETIME_SITE=info`, makes `dist-info/` (the info site: `how-it-works.html`, `privacy.html`, `404.html`); `src/web/` is shared and `__SITE__` (`"app" | "info" | "selfhost"`, a Vite define) selects behaviour. No framework, no runtime dependencies.
- Cloudflare Pages Function `functions/api/[[path]].ts` → router `handle(request, store, ctx, options)` in `src/worker/index.ts`; `public/_routes.json` limits the Function to `/api/*`. The router is runtime-neutral (no `node:` or `cloudflare:` imports, a test enforces it) and talks to a `SecretStore` (`src/worker/store.ts`): `store-d1.ts` for Pages, `server/store-sqlite.ts` for self-hosting. Both keep the same single SQL statements.
- D1 database `onetime` (binding `DB`), schema in `migrations/`. `0002_counter.sql` adds `stats(stored)`, kept exact by triggers on `secrets`; the capped insert reads it instead of `COUNT(*)`, so the cap counts stored rows (expired, not yet purged ones included). It must be applied remotely (`pnpm db:migrate:remote`, owner approval) before the deploy that contains it.
- Tests: two Vitest configs. `vitest.config.ts` runs in the Workers runtime via `@cloudflare/vitest-plugin` (no DOM, D1); `vitest.node.config.ts` runs `test/node/` in Node (SQLite store, Node server, site profiles). The API contract suite `test/contract/api-contract.ts` runs against both stores, including concurrency and a structural check that reveal and capped insert are single statements. Put testable browser logic in DOM-free modules under `src/web/`; `main.ts` is wiring only. The router takes `options { now, maxStored }` as test hooks.
- pnpm; build scripts for `esbuild` and `workerd` are allowed in `pnpm-workspace.yaml`.

## Command-line client

- `cli/core.ts` (pure, tested in the Workers runtime with `fetch` wired to the real router) and `cli/main.ts` (Node entry). `tools/build-cli.mjs` bundles them with esbuild into `dist/cli/onetime.mjs`, plus `onetime.cmd` (Windows shim) and `onetime.mjs.sha256`; the site serves them at `/cli/`. Node 22+ is the only requirement; no runtime dependencies.
- It reuses `src/web/crypto.ts`, `generate.ts`, `link.ts` and the shared limits, so links are interchangeable with the web page. Do not fork the crypto; change the shared modules and keep both sides tested.
- Rules: the secret is never accepted as an argument (stdin or hidden prompt only); stdout carries only the link (`send`, `gen`) or only the secret (`get`); hints on stderr never contain the link or key; server replies are size-capped and the returned id is validated; https only, except an explicitly named local server.
- `pnpm build` = `vite build`, then `build:cli` (vite empties `dist/` first), then `build:info` (`dist-info/`). `dev`, `deploy` and `deploy:info` go through `pnpm build`.
- Run on Linux only so far; Windows and macOS are untested (the README says so).

## Blob format v2 (docs/plans/blob-v2.md)

- The link says which format a blob has: `#<id>.<key>` is v1 (read forever), `#2.<id>.<key>` and `#2p.<id>.<key>` (passphrase needed) are v2. Never guess the format from the blob: any first byte or size can be a v1 blob. Old parsers reject three segments before anything is revealed, so keep the prefix form.
- `src/web/crypto.ts`: `createCodec`, `WRITE_FORMAT` (2 since deploy 2), HKDF-SHA-256 key, PBKDF2-SHA-256 600,000 rounds with a passphrase (salt derived from the link key, so the slow step runs before Reveal), padded to 256 B / 1 KiB / 4 KiB / 16 KiB + 4, format and flag bytes bound in as AAD. The independent `node:crypto` implementation in `test/node/crypto-v2.test.ts` is what proves the format; workerd refuses high PBKDF2 counts, so Workers-runtime tests use the `pbkdf2Iterations` hook (`Io.pbkdf2Iterations` in the CLI, never set by `cli/main.ts`; a test enforces that, and the same for `Io.writeFormat`).
- `MAX_TEXT_BLOB_BYTES` is 16,418 (largest text blob); `MAX_BLOB_BYTES` is 262,562 (largest hosted file blob; self-hosted servers go up to `FORMAT_MAX_BLOB_BYTES` 5,243,298). The server never checks bucket sizes. A wrong passphrase burns the secret by design.
- Deploy 1 read both formats and wrote v1; deploy 2 flipped `WRITE_FORMAT` to 2 and the texts (passphrases live). Do not roll back past deploy 1 while v2 links may still be unexpired.

## File transfer (docs/plans/file-transfer.md, writers live since deploy F2)

- Links: `#2f.<id>.<key>` and `#2fp.<id>.<key>` (passphrase). Flags byte: bit 1 = file, bit 0 = passphrase bound; both are in the AAD. Name and MIME type live inside the encrypted padded payload (`src/web/file-payload.ts`); names are cleaned by `safeFileName` (`src/web/filename.ts`, shared with the CLI).
- Files are offered only as downloads through `src/web/download.ts`, the only module allowed to call `URL.createObjectURL`/`revokeObjectURL` (test-enforced), always an `application/octet-stream` Blob via `<a download>`. Never preview or render a file: no `blob:`/`data:` URLs in `src`, no iframe, object, embed, img, media or srcdoc for it, no `window.open` or `location` to a file, no `innerHTML` with the name. The CSP is unchanged and has no `blob:`/`data:` (check-dist fails on them).
- Limits (owner decision 2026-11-20, `docs/plans/file-transfer.md` Deviations, branch `feat/large-files`): hosted `MAX_FILE_BYTES` 262,144 (blob 262,562), `FORMAT_MAX_FILE_BYTES` 5 MiB (blob 5,243,298; readers accept up to it; `FILE_BUCKETS` has 2, 4 and 5 MiB classes). Hosted files last 1 hour: a blob over 16,418 bytes with a TTL over 3600 gets 409 `maxTtl: 3600` (`LARGE_MAX_TTL_SECONDS`, router option `maxFileTtl`); texts keep their TTLs. Byte budget: 400 MB total, and blobs over 16,418 bytes only while the total is at most 200 MB. The 256 KiB hosted value needs a re-spike (A0 lost 1 reveal to error 1102 at 256 KiB, before the reveal path was made cheaper) before it is deployed; if it fails, lower `MAX_FILE_BYTES` and the rest follows.
- `GET /api/limits` (shared router, GET only, `no-store`, noindex) answers `{ maxFileBytes, maxFileTtl, maxTextBytes }` from the router options (`maxFileBytes`, `maxFileTtl`; `maxFileBytes` is 0 when files are off, by `maxFileBytes: 0` or `maxLargeBytes: 0`). `parseLimits`/`HOSTED_LIMITS` in `src/shared/limits.ts`, `fetchLimits` in `src/web/api.ts` (1 KiB cap, null on anything invalid). Clients fall back to `HOSTED_LIMITS` when it is missing. Do not hard-code the file limit in a client; ask the server.
- Self-host settings: `ONETIME_MAX_FILE_BYTES` (default 262,144, ceiling 5,242,880, above it exit 2, 0 = files off), `ONETIME_MAX_FILE_TTL` (default 3,600 like hosted, 60 to 604,800), `ONETIME_MAX_STORED_BYTES`, `ONETIME_MAX_LARGE_BYTES` (0 = files off too; either at 0 zeroes both; must hold one blob of the file size), `ONETIME_MAX_UPLOADS`. The upload body limit is `fileBlobBytes(maxFileBytes)`; the server request timeout is `requestTimeoutMs` (60 s plus 1 s per 32 KiB above a text blob, 220 s at 5 MiB).
- `migrations/0003_bytes.sql` (applied to the production D1 on 2026-11-20) adds `stats.bytes`. Counter repair also sets `bytes = (SELECT COALESCE(SUM(length(blob)),0) FROM secrets)`; a missing row is re-created with `INSERT INTO stats (id, stored, bytes) SELECT 1, COUNT(*), COALESCE(SUM(length(blob)),0) FROM secrets`.
- Abuse procedure: reports go to the privacy page's `#abuse` contact (app footer "Report abuse"). Delete by id only and never open a reported link with its key: `node tools/burn-id.mjs https://onetimepass.pages.dev '<id-or-link>'` (sends only the id, prints `deleted` or `not stored`; accepts `<id>`, `<id>.<key>`, `<fmt>.<id>[.<key>]` with fmt 2, 2f, 2p, 2fp, also after `#` in a URL). Fallback, with the owner's approval: `wrangler d1 execute onetime --remote --command "DELETE FROM secrets WHERE id = '<validated id>'"`.
- CLI 0.3.0 has `send --file`, `--name` and `get -o` (exclusive 0600 writes, target checked before the reveal). Links made since deploy F2 need 0.3.0; older versions report them as damaged without using them up. CLI 0.4.0 asks `GET /api/limits` before `send --file` (after the TTY/passphrase checks, before reading the file), refuses an over-limit file, files-off and an explicit `--ttl` above `maxFileTtl` before uploading, falls back to `HOSTED_LIMITS` for an older server, and reads files up to 5 MiB; 0.3.0 reads at most 1 MiB.

## Self-hosting (added 2026-11-19)

- Guide: `docs/self-hosting.md`; plan, decisions and recorded test results: `docs/plans/self-host.md` (incl. Deviations sections).
- Node server `server/` (plain `node:http`, no runtime deps, Node 22.13+; Docker uses Node 24), bundled by `tools/build-server.mjs` into `dist-server/server.mjs`. It loads `dist-selfhost/` into memory at start (no filesystem lookups per request), applies `public/_headers` with Pages' merge and `!` detach semantics, mimics Pages URLs (extensionless, 308s, `404.html` with 404), logs nothing per request, never reads Host/X-Forwarded-*. Over-limit bodies get 413 after a bounded drain. Exit codes: 2 config, 3 DB locked, 1 other.
- SQLite via `node:sqlite`: exclusive lock (one server per DB file; a second exits 3), WAL, `synchronous=FULL`, `secure_delete`, umask 077, migrations from `migrations/` tracked by `user_version`. Single instance only: no replicas, no network filesystems; managed container platforms (ECS Fargate/EFS, Azure Container Apps/App Service, Lightsail containers) are not supported until a Postgres store exists.
- Three site profiles from the same HTML (app, info, selfhost; the first two are the Pages sites and keep the `site:onetimepass` blocks) (`tools/site-profile*.mjs`, markers `<!-- site:onetimepass -->` / `<!-- site:selfhost ... site:selfhost -->`): `pnpm build` is the Pages site; `pnpm build:selfhost` needs `ONETIME_ORIGIN` (optional `ONETIME_OPERATOR_NAME`, `ONETIME_OPERATOR_CONTACT`, `ONETIME_INDEXABLE=1`), drops analytics, owner data and the Google CSP, and writes `_selfhost.json`; the server refuses any dist without it. Non-indexable builds (default) send `X-Robots-Tag: noindex` and `Disallow: /`.
- Analytics also has a runtime origin guard: it loads only on exactly `https://onetimepass-info.pages.dev` (off on the app origin, preview URLs and forks).
- Deploy files: `Dockerfile` (digest-pinned, non-root, `VOLUME /data`), `compose.yaml`, `deploy/onetime.service` (systemd, hardened), `deploy/Caddyfile.example`, `deploy/nginx.conf.example` (access logs off; nginx default sites must be removed). AWS/Azure VM instructions and running the systemd unit are untested (the guide says so).
- `packageManager` pins pnpm 12.16.1; `pnpm install --frozen-lockfile` needs the lockfile's `packageManagerDependencies` block.
- Text changes on the pages must keep all three outputs true; check-dist checks all three.
- Deploy code (Helm, Ansible, Terraform) has the file limit as a variable: Helm `config.maxFileBytes`/`config.maxFileTtl`, Ansible `onetime_max_file_bytes`/`onetime_max_file_ttl`, Terraform `max_file_bytes`/`max_file_ttl` (defaults 262144 and 3600, ranges validated). Proxy and ingress body limits are derived, never hard-coded: largest blob (`fileBlobBytes`) plus 3 %, rounded up to 100 KiB (307200 default, 5427200 at 5 MiB); proxy read/send timeouts = app request timeout + 10 s rounded up to 10 s (80 s default, 230 s at 5 MiB). Overrides: `ingress.maxBodyBytes`/`ingress.proxyTimeoutSeconds`, `onetime_max_body_bytes`/`onetime_proxy_timeout`, `max_body_bytes` (a body limit below the blob is refused). The Caddy/nginx examples use 300k / 80 s.

## Known open points

- No per-IP rate limit (the Workers rate-limit binding is not available on Pages, and WAF rules need a custom domain). A global cap of 20,000 stored secrets returns 503 when full, so the cap can be filled by an attacker. Near-full rule: while more than 80 % of the cap is in use (`longTtlCap`, 16,000), `POST /api/secrets` with a TTL over 1 day is refused with 409 and `maxTtl: 86400` (never clamped; same single capped insert with a smaller cap; the web page switches the expiry to 1 day and waits for a second Create, the CLI exits 5 with a `--ttl 1d` hint). The account is on the D1 free plan (5 million rows read, 100,000 rows written per day; past either, queries fail until 00:00 UTC, reveals included): the counter row removes the read amplification, but the daily write quota stays an open denial-of-service path that only a rate limit (custom domain + WAF) or a paid plan closes. D1 Time Travel is 7 days on the free plan, as the page and README say.
- Back-button (bfcache) clearing: the page clears secrets, links, passphrases and files on `pagehide` and again on every `pageshow` (WebKit restores form state after Back), and those fields are `autocomplete="off"`. Chromium: a real restore was proven with a test-only proxy that removes Cache-Control (`test/e2e/bfcache.spec.mjs`); with the live `no-store` headers Chromium keeps the pages out of the bfcache. Firefox and WebKit could not be proven to do a real restore under Playwright (Firefox cannot observe it; the WebKit runs showed the form-state restore only); the clearing assertions hold in all three.
- Browser e2e: `pnpm e2e` (`test/e2e`, Playwright-core, Chromium + Firefox + WebKit against a built self-host server; `E2E_BROWSERS`, `E2E_SPEC`, `E2E_NO_BUILD` select/skip). It is not part of `pnpm check` and not in CI yet. WebKit needs its system libraries (`playwright-core install-deps` on a normal host; without root, `E2E_WEBKIT_LD_PRELOAD` as described in `test/e2e/run.mjs`).
- File blobs of 256 KiB+ lost data to Cloudflare error 1102 (CPU limit) on the free plan in the A0 spike (256 KiB: 1 of 59 reveals lost). Hosted files are 256 KiB by owner decision (2026-11-20) and the reveal path was made cheaper, but it is not re-measured: re-spike (A0 at 256 KiB, free plan) before the hosted deploy, and lower `MAX_FILE_BYTES` if it fails.
- Some Node tests start real servers and can time out when the machine is very loaded (load average 40+); a rerun passes.
